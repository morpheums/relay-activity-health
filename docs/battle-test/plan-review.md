# Adversarial plan review (reviewer, Sonnet 5) — verbatim final report

Reviewed PLAN.md at commit 7ca4f8a against Requirements.md and the seed.

## Ranked findings
**1. Statistics/product — the √-floor makes "below normal" nearly unreachable for low-volume series, defeating the "which location needs attention" goal.** For any series with median ≈1–2 (common for small sites — per-site weekly medians are stated as 3–6), `spread = max(1.4826·MAD, √median) ≥ 1`, so `low = max(0, ⌈median−2·spread⌉)` clamps to 0. A site with baseline median 1 has band [0,3] — a week where it goes completely silent (count 0) reads as "Normal." The one failure mode a Monday-morning admin most needs (a location going dark) is invisible for exactly the low-count locations where it matters most. Not discussed in §5.3 or §4. Suggest: flag count=0 as its own state when the baseline median is materially non-zero, independent of the band math.
**2. Spec precision — `baseline: null` on insufficient_data contradicts §5.4's own UI requirement.** §5.2 says "`baseline` is `null` when insufficient." §5.4 requires displaying "Not enough history (3 of 4 weeks)" — but if `baseline` is entirely null, `weeksUsed` (the "3") has nowhere to live in the contract. Two engineers resolve this differently: one nulls the whole object (frontend can't show the count), another keeps `weeksUsed` and nulls only the stats. Fix: always populate `baseline.weeksUsed`; null only `median`/`low`/`high`.
**3. Spec precision — `earliestWeek` is undefined.** It appears only in the example JSON, never in the param-rules table. Is it global (dataset start) or per-account (first-activity week)? What happens when `week` precedes it — 400, like "after latest complete week," or a 200 with empty locations? The rules table states the *after* case but not the *before* case. This is exactly the kind of gap the review brief calls out, and it's missing.
**4. Brief compliance — no agent owns two required README sections.** The brief requires "how to run it locally (DB setup, env vars, commands)" and "notable choices within the stack... and why." `product.md`'s remit is explicitly interpretation/assumptions/decisions/deferred — it doesn't cover run instructions or stack rationale (ORM vs. raw SQL is the architect's/database's call, not product's). §9 Phase 3 only assigns "product: README." Nobody is tasked with the setup section, and a missing one is a submission blocker.
**5. Process risk — DB tooling is the heaviest-invested layer exactly where the brief says not to spend budget.** "SQL Server is a nice touch... don't burn your time budget on DB setup" — yet the plan mandates docker-compose SQL Server, Testcontainers-only integration tests (CLAUDE.md rule 6 forbids InMemory/SQLite), a custom embedded-seed migration, index-plan verification, and DST-boundary tests across two timezones. With ~3h left, 4 test layers, and 7 agents with review checkpoints, this is the most likely place the plan overruns — and unlike frontend tests or the type filter, DB rigor isn't in the §10 cut line at all.
**6. Product judgment — ranking treats "above" and "below" symmetrically.** §5.3 step 8 sorts by |deviation| alone, so a location having a lucky busy week ranks as needing "attention" identically to one that's quietly failing. Defensible (a spike can also signal a problem), but never argued against the ticket's actual framing, unlike D2/D3/D7 which do defend their choices.
**7. Statistics — D7's calibration only covers the easy case.** The 4.8%/15.1%/34.6% figures come from site-weeks with a *full* 8-week baseline; the system also serves the 4-week minimum, where MAD is far noisier, and that worst case was never simulated.
Areas that are fine: D6 (SQL counts only, C# does the math) is a clean, testable boundary — no issues. The worktree/file-scope separation in §9 has no actual collision risk (disjoint paths, only architect touches shared files).
