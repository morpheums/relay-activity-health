**Recommended query (c)**, run through both `sp_executesql` and EF Core 10 `Database.SqlQuery<T>`:
```sql
SELECT deduplicated.location, deduplicated.window_start, COUNT(*) AS event_count
FROM (
    SELECT DISTINCT windows.window_start, events.location, events.event_type,
           events.occurred_at, events.duration_seconds, events.outcome
    FROM OPENJSON(@windows) WITH (window_start datetime2 '$.start', window_end datetime2 '$.end') AS windows
    JOIN activity_events AS events
      ON events.account_id = @accountId
     AND events.occurred_at >= windows.window_start
     AND events.occurred_at <  windows.window_end
    WHERE @eventType IS NULL OR events.event_type = @eventType
) AS deduplicated
GROUP BY deduplicated.location, deduplicated.window_start
```
Through EF, a null `eventType` works, and account 6's results match `counts.csv` exactly. I recommend OPENJSON over a table-valued parameter: a TVP would also need a user-defined table type in a migration.

**`counts.csv`:** 5,851 non-zero rows. A separate Python recount from the raw rows gives identical results. Account 6 has 880 events in the week of Jun 1 and 87 in the week of Jul 20, matching PLAN §2/§5.2. Account 20 has no rows.

**Checks:**
- **Exact duplicates:** SQL Server finds 12 pairs (12,614 distinct rows). A case-sensitive comparison finds the same 12.
- **1538/1539** count once: account 4, Site B, week of Feb 23 goes from 8 to 7.
- **5856/5857** count once: account 1, Site F, week of Apr 27 goes from 14 to 13.
- **Naive dedup:** a self-join using `=` finds only 8 pairs, and the `NOT EXISTS` form keeps 12,618 rows instead of 12,614. The 4 pairs it misses all have a NULL column. The correct forms are `DISTINCT` or, for joins, `IS NOT DISTINCT FROM`.
- **Window boundary:** an event exactly at a window start lands in that window; one 100 ns earlier lands in the previous window.
- **Execution plan with the planned index:** Clustered Index Scan of `PK_activity_events`, with the OPENJSON function re-run 2,641 times on the inner side of a Nested Loops join (about 200 ms). The dedup needs `duration_seconds` and `outcome`, which the index doesn't include, so SQL Server skips it.
- **Execution plan with those two columns added to the index:** Index Seek on `account_id = @accountId, occurred_at >= window_start, occurred_at < window_end`, run once per window (26 times), about 7 ms. Query (b) already seeks; query (a) scans the index, which is fine at this size.

**Datatype and collation surprises:**
- **Case and trailing spaces are ignored:** `'CALL_RECEIVED'` and `'site a   '` both match. The seed data is clean, but the API must check `type` against the exact values itself.
- **Time zone offsets are dropped silently:** OPENJSON turns `-05:00` into the local time, not UTC. Windows must be sent as UTC with a trailing `Z`.
- **Read-back times aren't marked UTC:** EF returns them as `DateTimeKind.Unspecified`, so they need `SpecifyKind(Utc)`.
- **Type mismatch:** EF sends strings as nvarchar, so SQL Server converts the varchar column on every comparison. It's harmless today.
- **`datetime` would break the seed:** under a British language setting it fails on the seed's date strings. Keep `datetime2`.

**What the plan should change:**
1. §5.1: make the index `INCLUDE (location, event_type, duration_seconds, outcome)`. As written, it contradicts the performance intent.
2. Allow only `DISTINCT` or `IS NOT DISTINCT FROM` for dedup, and forbid `=`-based joins or `NOT EXISTS`.
3. Infrastructure: send windows as UTC JSON, mark read-back times as UTC, and only call `ToListAsync()` on the raw SQL. If EF adds anything else, it wraps the SQL in a subquery, which breaks with a trailing `;` or `ORDER BY`.
4. §6 says the anchor query returns "data anchor + first event", but the account's first event can be taken as the MIN over query (b). Decide which query supplies it.
5. Query (b) ignores the type filter, so a site counts as existing whatever type is selected. Confirm that's what §5.3 step 1 means.
