### 🤖 ASSISTANT — 2026-09-29T09:15:21.352Z

I found five efficiency issues worth fixing, plus one budget point for context. I read the diff and measured the inline style sizes in the worktree. `node_modules` isn't installed, so I did not build or measure real bundle sizes. Everything else is clean, and I've listed it at the end.

**Worth fixing, most impactful first**

1. `web/src/app/app.routes.ts:6` — The lazy `loadComponent` for `dashboard` is the app's only route.
   - **Cost:** The initial JS load becomes two sequential requests: the main chunk, then the dashboard chunk. Nothing is deferred, because the dashboard chunk holds everything heavy: Material datepicker, CDK overlay, date-fns and the adapter.
   - **Cheaper:** Either go back to the eager import, or load only the heavy part lazily. For the second option, wrap `<mat-calendar>` in `@defer (when isOpen())` inside the overlay template in `week-picker.ts:581`. Material's calendar code then downloads on the first click to open the picker, not on page load.

2. `web/angular.json:22-25` — `@fontsource/geist/400.css`, `500.css` and `600.css` are the all-subsets files.
   - **Cost:** Each file declares an `@font-face` for every unicode subset. That means about 3× the CSS in the blocking global stylesheet, and every subset's font files get copied into the build output. The app is English-only, so only latin is ever fetched.
   - **Cheaper:** Use `@fontsource/geist/latin-400.css`, `latin-500.css` and `latin-600.css`. I assumed those file names exist in the installed 5.3 package but couldn't confirm it without `node_modules`.

3. `web/src/app/features/dashboard/week.ts:51-55` and `week.ts:38` — `formatCalendarDayPair` builds two `new Intl.DateTimeFormat` objects per call, because `calendarDayParts` constructs one each time. The zone is hardcoded to `'UTC'` here.
   - **Cost:** The diff adds `WeekPicker.weekLabel`, which calls this once per week change, so it now builds two formatters per step. `selectableWeeksLabel` (`week-picker.ts:636`) adds two more each time an account change re-evaluates it with the overlay open. Constructing `Intl.DateTimeFormat` is the slow part of formatting.
   - **Cheaper:** Hoist one module-level `Intl.DateTimeFormat('en-US', { …, timeZone: 'UTC' })` and reuse it for the pair formatting. Only `formatCalendarDay` needs a per-zone formatter, and a `Map<timeZone, DateTimeFormat>` would cache those.

4. `web/src/styles.scss:1053-1135` plus `week-picker.ts:600` — The picker's overlay styles (about 2.5 kB of `.week-picker-dialog` rules, the `@keyframes` and the reduced-motion media query) sit in the global stylesheet.
   - **Cost:** That stylesheet is render-blocking on every page load, including for users who never open the picker. The styles are there only because overlay content escapes component encapsulation.
   - **Cheaper:** Move those rules into `WeekPicker`'s `styles` with `encapsulation: ViewEncapsulation.None`, so they ship with the component. Combined with finding 1, they would travel with the lazy code.

5. `web/src/app/features/dashboard/components/week-picker.ts:549` — `A11yModule` is imported for a single directive.
   - **Cost:** This is the whole-module import the checklist warns about, so it pulls in everything the module declares. The bundler has to drop the unused parts, and `A11yModule` re-exports several directives.
   - **Cheaper:** `imports: [CdkTrapFocus, …]` from `@angular/cdk/a11y`.

**Budget point for context, not a defect:** `dashboard.page.ts` carries about 5.8 kB of raw inline styles. Angular measures after minification, so it is somewhat under, but it uses nearly all of the raised 6 kB warning limit. About 1.7 kB of that is loading skeletons and about 2.2 kB is footer styling. The status badge rules are also written twice, in `account-summary.ts:160-163` and `location-table.ts:500-502`. Moving the shared `.status-badge` and `.card` rules into one place would cut total bytes, but moving them into new components would not.
